# 訂單業務規則

## 取消訂單

**API Endpoint：** `PATCH /api/orders/{order}/cancel`

### 1. 功能概述

會員可以取消符合特定條件的訂單。

取消訂單時，系統必須確保訂單狀態、付款狀態、付款交易、物流資料及商品庫存維持一致。

### 2. 訂單取消資格

訂單必須同時符合以下所有條件，才允許取消：

1. 訂單屬於目前已登入的會員。
2. 訂單尚未被取消。
3. 訂單狀態為「產品備貨中」。
4. 訂單付款狀態為「未付款」或「付款失敗」。
5. 訂單所有付款交易的狀態皆不為「已授權」或「已付款」。
6. 訂單不存在任何物流資料。

只要其中一項條件不符合，就必須拒絕取消訂單。

已取消訂單不再執行取消，但適用第 4 節的冪等回應，不以一般資格衝突回覆。

付款交易與物流紀錄僅檢查該筆訂單，不得因同會員或其他會員之別筆訂單存在已授權、已付款交易或物流而阻擋。

- 沒有付款交易不影響取消資格。
- 任一筆交易為「已授權」或「已付款」即拒絕，不得只檢查最新一筆交易。
- 即使訂單付款狀態仍為「未付款」或「付款失敗」，已授權／已付款交易仍須阻擋取消。
- 「待建立付款」、「付款失敗」、「已取消」、「已過期」、「已退款」交易不會單獨阻擋取消。
- 「已退款」交易可與符合資格的訂單一起保留；取消不得改寫退款時間或歷史。
- 任何狀態的物流紀錄皆阻擋首次取消，包括已失敗、已退回及已取消的物流。

### 3. 訂單所有權驗證

會員只能取消屬於自己的訂單。

系統必須驗證目前登入會員與指定訂單之間的所有權關係，不得僅依賴客戶端提供的訂單 ID。

### 4. 防止重複取消

已取消的訂單不得再次執行取消操作。

系統必須確保同一筆訂單不會因為重複請求而重複回補商品庫存。

即使多個取消請求同時執行，也只能有一個請求成功完成訂單取消及庫存回補。

重複請求及並行請求可皆回傳 `200 OK`，但只能有一個請求實際改變訂單狀態與回補庫存。已取消訂單的後續請求不得再次改寫訂單、付款交易或庫存，即使留有異常物流紀錄亦同。

### 4.1 成功取消的資料結果

- 訂單狀態改為「已取消」。
- 訂單付款狀態保留原本的「未付款」或「付款失敗」，不自動變成「已退款」。
- 所有「待建立付款」的交易改為「已取消」。
- 已失敗、已取消、已過期及已退款交易歷史保持不變。
- 明細快照與總額保持不變。
- 不得建立物流或發送外部物流請求。
- 取消後才處理的 `OrderCreated` 事件不得再建立付款交易。

### 5. 商品庫存回補

取消訂單時，必須將該訂單所占用的商品庫存回補。

庫存回補必須與訂單取消操作保持資料一致性：

- 每筆訂單只能回補一次庫存。
- 訂單取消與庫存回補必須在同一個資料庫交易中完成。
- 若取消流程發生資料庫錯誤，庫存回補及訂單狀態變更必須一併回滾。

### 6. 資料庫交易

取消訂單必須使用資料庫交易，確保相關資料操作具備原子性（Atomicity）。

若交易中的任何 SQL 語句執行失敗，必須完整回滾，不得留下部分更新的資料。

訂單狀態、待付款交易及所有商品庫存必須共同成功或共同回滾；不可依賴測試框架的外層 transaction。即使已回補兩個不同商品後才發生 SQL 錯誤，也須還原兩筆庫存。伺服器錯誤不得向 client 暴露 SQL、exception 或 stack trace。

### 7. 併發控制

取消訂單必須防止與其他可能操作相同訂單或相關資源的功能產生競態條件（Race Condition）。

#### 7.1 資料庫鎖定

- 必須透過適當的資料庫鎖定機制，避免多個請求同時修改相同訂單。
- 必須確保訂單取消、付款處理、物流處理及庫存異動等相關功能之間的資料一致性。
- 資料庫鎖定順序必須與其他可能產生競態條件的功能保持一致，避免因鎖定順序不一致而產生死結（Deadlock）。
- 鎖定範圍必須涵蓋取消資格檢查及相關資料更新，避免檢查完成後、更新之前發生競態條件。

現有取消／付款／物流防禦測試以同一筆 Order 的 row lock 作為共同協調點，先鎖訂單，再檢查及修改相關資料。等待鎖期間若訂單付款、付款交易、訂單狀態或物流資料改變，必須取得鎖後重新檢查。

取消流程在持有訂單鎖的同一 transaction 內同步處理 `OrderCanceled` 事件，取消待付款交易、回補庫存並標記訂單已取消；不可將這些操作改成獨立的 queued listener。待付款交易先依該訂單取得主鍵，再以主鍵更新，避免非唯一狀態索引的範圍鎖阻塞其他訂單取消。

此規則不要求新訂單結帳先鎖尚不存在的 Order；結帳與取消共用的商品庫存，必須維持相同的商品鎖定順序。

#### 7.2 商品庫存一致性

當多個請求同時嘗試取消相同訂單時，必須確保只有一個請求能夠完成庫存回補。

當取消訂單與其他庫存異動功能同時執行時，也必須確保庫存數量正確，不得發生遺失更新（Lost Update）或重複回補。

庫存以 atomic operation 更新，商品規格 ID 由小至大處理，與結帳扣庫存順序一致。不同會員的訂單共用商品時，不論結帳扣庫存或取消回補先執行，最終庫存皆須等於原庫存加回補量再減購買量。

不同訂單同時取消且共用商品時，各自須先鎖定自己的訂單，再依相同商品 ID 升冪回補各自明細數量。即使兩筆訂單的明細儲存順序相反，也不得遺失更新、重複回補或因商品鎖順序相反而死結。例如初始庫存為 10／20、兩筆訂單各回補 2／3，最終須為 15／25，兩筆訂單及其待付款交易皆取消。

原本庫存不足時，checkout 與取消回補的預期依資料可見時點區分：

- 回補 transaction 已提交，checkout 才開始交易內的訂單／庫存查詢：應使用回補後庫存；足夠時可建立訂單。測試以兩商品初始庫存各 1、各回補 2、各購買 3 驗證，checkout 回傳 `201`，最終庫存各 0。
- checkout 已讀到各 1 的不足庫存，而回補尚未提交：checkout 回傳 `409`，不建立訂單、明細或付款交易，也不扣庫存。取消提交後，最終庫存各 3。
- 不得預支另一個 transaction 尚未提交的回補，也不要求已判定庫存不足的 checkout 自動等待或重試。不能僅依 HTTP 請求抵達順序判定結果，亦不保證既有 transaction 的讀取快照會看見稍後提交的回補。

#### 7.3 付款處理競爭

- 付款成功或授權先成立時，取消須拒絕且不回補庫存。
- 付款失敗先成立時，若其他資格成立仍可取消，並保留失敗交易歷史。
- 取消先成立時，不得再建立進行中的付款交易；取消前已由重試建立的待付款交易須一併取消。
- 目前測試保留已取消交易收到付款回呼時回覆 `400` 的既有契約，但這不代表外部付款已被撤銷，也不構成完整對帳／退款方案。

#### 7.4 物流處理競爭與延遲工作

- 延遲的物流建立工作與取消必須共用訂單鎖；物流先成立則取消回傳 `409`。
- 取消先成立時，過期的付款成功事件不得再建立或送出物流單。
- 待送單工作取得鎖後必須重新檢查訂單。若訂單已取消，即使有殘留的待送物流紀錄及有效 payload，也不得發送外部請求或改寫物流。
- 已開始送單且有物流紀錄時，會員取消須拒絕，不得回補庫存。
- 已取消訂單若收到簽章有效的配送中／已送達回呼，回覆 `200`、`1|OK`，保持訂單、物流、付款交易及庫存不變。
- 物流回呼先處理配送／送達狀態時，後續取消須拒絕且不回補庫存。
- 不允許因延遲物流回呼將已取消訂單恢復為配送中／已送達。
- 物流送單工作及物流建立通知只在來源 transaction 提交後排入 queue；rollback 時不得送單或通知。
- 送單 worker 取得訂單鎖後重新讀取物流資料，只送出仍為待建立且訂單未取消的物流。鎖持續至外部請求及本機結果更新完成，以協調同筆訂單的取消與其他送單工作；這不代表資料庫能回滾已完成的供應商操作。

上述殘留物流及過期事件情境屬防禦性處理，不表示正常取消流程允許存在物流紀錄。

### 8. 路由參數驗證

取消訂單 API 使用路由參數 `{order}` 指定訂單。

- `{order}` 必須符合路由定義的合法格式。
- 不合法的路由參數格式必須回傳 `404 Not Found`。
- 指定的訂單不存在時，必須回傳 `404 Not Found`。

### 9. 請求頻率限制

取消訂單 API 必須套用 Rate Limiting，避免短時間內大量請求影響系統穩定性。

Rate Limiter 的限制次數及時間間隔應以實際設定為準。

目前 `orders` 寫入限流為每會員每分鐘 10 次、每 IP 每小時 50 次。取消與付款交易建立等訂單寫入共用額度；訂單讀取使用不同額度。超限回傳 `429` 與 `Retry-After`，不得執行取消。到期後恢復操作，不同會員及 IP 須依這兩個識別鍵隔離。

### 10. 身份驗證及回應契約

- 正式 SPA 使用 Session Cookie；不要求 Personal Access Token。
- Session 失效或未登入時回傳 `401`。
- Stateful PATCH 的 XSRF Token 缺失或不正確時回傳 `419`，不得修改資料。此檢查可能先於身份驗證執行。
- 他人訂單與不存在的訂單回傳 `404`；格式非法的路徑在登入前後皆回傳 `404`。
- 首次成功取消與已取消的冪等回應皆為 `200`；不符合首次取消資格回傳 `409`。
- 成功回應包含 `message`；其他欄位與固定訊息文字不在目前測試契約內。

對外使用方式見 [取消訂單 API](../api/orders.md)，身份驗證架構見 [authentication](../architecture/authentication.md)。

### 11. 尚未定義的範圍

外部付款已成功、但通知在取消後才抵達時，仍需定義付款事實的保存、對帳、退款或人工處理。資料庫鎖只能協調本機操作；不得將回呼 `400` 視為款項已退還或未收取。
